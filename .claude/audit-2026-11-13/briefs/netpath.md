## [high] (network path) LAPTOP-MSLI2NU1 egress — Windows 11 + WSL2 Ubuntu; no repo file implicated:None
**Summary**: Root cause (reproduced): this egress silently blackholes TLS ClientHellos whose SNI is exactly 'controlplane.tailscale.com' — identical behavior from Windows and from WSL2 (WSL NATs through Windows). Both tailscaled instances are therefore logged out (BackendState=NoState) with no netmap; WSL's tailscale0 holds no 100.x address, so the A10 and every tailnet peer are unreachable. 'no matching peer' + TCP failures are symptoms of the dead control channel, NOT of Windows claiming 100.x routes (Windows has zero 100.x routes).
**Failure scenario**: WSL→A10 over tailscale: `tailscale status` => 'You are logged out. The last login error was: fetch control key: Get https://controlplane.tailscale.com/key?v=148: context deadline exceeded' / 'unexpected state: NoState'; `tailscale ip` => none; `ip route get 100.68.122.100` => via 172.27.176.1 dev eth0 (default Wi-Fi gateway, no tailscale0 path); `ping -c2 100.68.122.100` => 100% loss; WSL journald has 194 'fetch control key ... deadline exceeded' events (first 2026-11-13T09:51:34Z) and 3x 'ping(100.68.122.100): no matching peer' (10:11–10:21Z). Discriminator: TCP connects to the control LB 192.200.0.104, but the TLS handshake hangs ONLY when SNI=controlplane.tailscale.com (ss -tin during stall: hello segment retransmitted 8x, bytes_retrans 2624, segs_in=1); the SAME IP with no SNI completes TLSv1.3 (cert CN=controlplane.tailscale.com, Let's Encrypt YE1) and GET /key returns 200 {"legacyPublicKey":"mkey:9e5..."}. The same-SNI drop also occurs toward github.com/1.1.1.1/8.8.8.8 (which answer with other SNIs), and external vantage points (check-host.net ch/es/ir/se/us) get 302 from https://controlplane.tailscale.com/ — so this is a local-path payload-scoped drop, not a Tailscale outage, DNS, or cert problem.
**Check command**: `REPRO (read-only) — [WSL]: openssl s_client -connect 192.200.0.104:443 -noservername -brief </dev/null   # => TLSv1.3 OK, cert CN=controlplane.tailscale.com ; openssl s_client -connect 192.200.0.104:443 -servername controlplane.tailscale.com -brief </dev/null   # => silent hang / 0 bytes ; curl -sS -m 10 -o /dev/null -w '%{http_code}' https://controlplane.tailscale.com/key   # => 000 . [Windows PowerShell]: curl.exe -sS -m 10 -o NUL -w '%{http_code}' https://controlplane.tailscale.com/key   # => 000 (timeout) while curl.exe -sS -m 10 -o NUL -w '%{http_code}' https://example.com   # => 200 .
FIX, in order — (1) [Windows PowerShell, as Administrator]: tailscale down ; net stop Tailscale ; sc.exe config Tailscale start= demand    # stops the Windows node from ever re-owning 100.64/10 routes (it cannot log in through this network anyway).
(2) Move this laptop's Internet (Wi-Fi) to an egress that does not drop the Tailscale control SNI — e.g. phone hotspot; WSL2 NATs through Windows, so this single switch fixes both sides. Confirm with [Windows PowerShell]: curl.exe -sS -m 8 -I https://controlplane.tailscale.com/   # expect HTTP/1.1 302, not a timeout.
(3) [WSL (root)]: tailscale up --accept-routes --hostname=wsl-gpu-node    # login uses login.tailscale.com, which is NOT blocked.
(4) VERIFY [WSL]: tailscale ping -c 3 <A10-tailnet-IP-or-name>    # proves the overlay path end-to-end (DERP fallback ok); service-level alternative: timeout 6 bash -c 'echo > /dev/tcp/<A10-IP>/50051' && echo A10-REACHABLE . (<A10> = the A10's tailnet IP/name from `tailscale status`; if it never appears there, the A10 itself is not joined to this tailnet and must be joined from its side.)`
**Reproduced by auditor**: True

## [med] (environment) Windows routing table + WSL2 NAT:None
**Summary**: Secondary mechanism/risk: while WSL's tailscaled is logged out, all WSL traffic to 100.64.0.0/10 falls through to the Wi-Fi default gateway and is dropped; and any time the Windows tailscaled node is logged in while WSL's is not, the Windows Tailscale adapter owns 100.64/10 on the host and will silently carry/blackhole WSL's tailnet traffic (classic dual-tailscaled WSL2 hijack). Keep the Windows node stopped while WSL is the tailnet node.
**Failure scenario**: `ip route get 100.68.122.100` => via 172.27.176.1 dev eth0 (no tailscale0 route) + `ping -c2 100.68.122.100` => 100% loss — reproduced now. Windows currently shows ZERO 100.x routes (so the hijack is latent, not active), but PowerShell history shows the dual-daemon pattern in use (`net stop Tailscale` on Windows + `wsl ... tailscale up --accept-routes`), which is the configuration that produces the hijack whenever both are up and Windows' node wins the host routing table.
**Check command**: `[WSL]: ip route get 100.68.122.100 ; ping -c 2 100.68.122.100 | [Windows PowerShell]: route print -4 | findstr /r "^ *100\." ; Get-NetRoute -AddressFamily IPv4 | Where-Object DestinationPrefix -like '100.*'`
**Reproduced by auditor**: True
