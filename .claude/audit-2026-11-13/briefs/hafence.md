## [high] src/distllm/core/ha_coordinator.py:315
**Summary**: handle_heartbeat_request applies any sender's replicated state whenever the local node is FOLLOWER — there is no check that the sender is the leader, is in the current term, or that the state is newer (plain dict.update, last-writer-wins). _probe_peer attaches the local _replicated_state to every outbound probe, so follower-to-follower probes propagate stale state. The same applies via the live HTTP path: POST /api/v1/ha/heartbeat accepts a 'state' body from any holder of the HA secret (server.py:1562) and applies it without a sender-authority check.
**Failure scenario**: Failover: leader c pushed {'topology': 'v10'} to standbys a and b. c dies, b becomes leader. Old leader c (now a follower) still holds its stale {'topology': 'v7'} and keeps probing; when its heartbeat reaches standby b, b overwrites v10 with v7 (reproduced). Any demoted or lagging node can regress a standby's state, and the /api/v1/ha/snapshot equivalent (apply_state_snapshot) likewise has no sender-is-leader check.
**Check command**: `PYTHONPATH=src python -c "from distllm.core.ha_coordinator import RayFaultTolerance as R; b=R('coordinator-b'); b.handle_heartbeat_request('coordinator-c',9,{'topology':'v10'}); print('after leader push:',b.get_replicated_state()); b.handle_heartbeat_request('coordinator-a',1,{'topology':'v7'}); print('after stale follower probe:',b.get_replicated_state())"  # prints v10 then v7`

## [med] src/distllm/core/cluster_state_store.py:341
**Summary**: ClusterStateStore never renews its leader lease and never re-validates it: elect_leader() sets the leader key with ttl*2 and the lock with ttl, heartbeat() only refreshes the node key, and is_leader() is a purely local comparison (_leader_id == _node_id) that never re-reads the backend. After LEADER_TTL the lock/key expire, a second node elects itself, and the first still reports is_leader()=True — a stale leader that keeps writing. With no Redis the InMemoryBackend fallback is per-process, so every process self-elects.
**Failure scenario**: Node a elected leader (ttl=15 s). Its heartbeat loop refreshes only its node key; 30 s later the cluster:leader key expires. Node b's background loop sees no leader and elect_locals itself. Both a.is_leader() and b.is_leader() return True indefinitely, with no fencing token on the lock to reject a's late writes (lock has none; acquire is set-nx-ex only). In a multi-process deployment without Redis, a and b each hold private in-memory locks and both self-elect on first attempt.
**Check command**: `PYTHONPATH=src python -c "import time; from distllm.core.cluster_state_store import ClusterStateStore as S; a=S(cluster_name='c',node_id='a',redis_host='',ttl=1); b=S(cluster_name='c',node_id='b',redis_host=''); b._backend=a._backend; print('a elected:',a.elect_leader()); time.sleep(2.2); print('b elected after lease lapse:',b.elect_leader()); print('both leaders:',a.is_leader(),b.is_leader())"  # both leaders: True True`

## [med] src/distllm/core/split_brain.py:189
**Summary**: Fencing tokens are not durable and not comparable across nodes: _fence_token starts at 0 in every process (line 72), should_accept_request uses >= so token 0 — and anything, including a fenced-out leader's old token after restart — is accepted, and no node ever exchanges its token with peers. Additionally, nothing in src calls should_accept_request()/fence_request(): FederationCluster increments its private token on partition (federation.py:496) but no request path ever verifies a token, so the fence is write-only.
**Failure scenario**: Old leader is fenced at token 3; the fencing authority (or a follower enforcing it) restarts (crash, rolling deploy) and its counter resets to 0, so the fenced leader's next request with token 3 is accepted again. And because each cluster keeps a local counter that is never transmitted, token 3 at node X cannot be ordered against token 1 at node Y — a stale leader's writes are indistinguishable from the new leader's, which is the stale-leader tolerance this mechanism is supposed to prevent.
