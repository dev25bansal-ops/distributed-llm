# Action Plan 01 — Strategic Opportunities & Market Positioning

**← [[Exhaustive Audit 2026-08-11]]**


DistLLM's single defensible capability is heterogeneous consumer multi-device pooling (RTX/AMD/Apple Silicon/CPU over LAN/WiFi/Internet to run models no one machine can hold) — audit finding #225 confirms the codebase roughly matches that claim, and the README already anchors on it. But the build is 'wide, not proven': 792 source modules with dozens of decorative moonshot subsystems (Byzantine fault tolerance, DaaS marketplace, federated/DP, WAN disaggregation, WebGPU) exist while the measured evidence the whole pitch depends on is thin. The TWO hard truths: (1) performance credibility is the #1 adoption blocker — single-node throughput (92.0 tok/s on RTX 4090, BENCHMARKS.md:197) is uncompetitive, the canonical TTFT/ITL tables for 4090 and 2-node are still EMPTY (BENCHMARKS.md:127-135), the 70B '52-68 tok/s' scaling figures are 'illustrative' website numbers, not BENCHMARKS.md runs, and the only real scale-out number is sub-linear (2 nodes = 153.1 tok/s = 1.66x, 83.2% efficiency, BENCHMARKS.md:198); (2) docs over-claim vs reality — MARKETING.md references a src/distllm/billing package that does not exist (verified: NO billing dir), YC_STARTUP_PACKAGE asserts 'working product, real users,' and the June-2026 competitive-analysis omits the closest real 2026 competitor, exo (~46.8k stars, Apache-2.0, the same 'pool your devices' pitch on Apple Silicon). Strategic priorities: close the perf/evidence gap, make first-run win on 3 OSes, build the Ollama multi-device on-ramp as the distribution wedge, monetize the enterprise license + marketplace before the (unbuilt) managed cloud, add OpenAPI-gated SDK parity, and cut/defer the unverifiable surface.

## Moats / defensibility

- Complexity/runtime moat: reliable heterogeneous multi-device pipeline parallelism over lossy LAN/WiFi/Internet with auto-discovery, auto-partitioning, node recovery, straggler detection, and WAN token-accumulation is genuinely hard to build — Petals failed and every other consumer tool (exo, Ollama) is LAN-local or single-device.
- Backend-agnostic breadth: ~16 registered backend adapters (vLLM, llama.cpp, MLX, Ollama, NIM, TGI, Triton, TensorRT, ONNX, PyTorch, ExLlamaV2, WebGPU, etc.) means any hardware/quantization advance anywhere benefits DistLLM; exo is MLX-only and Ollama is llama.cpp-only.
- True heterogeneity vs exo: DistLLM runs pools of NVIDIA + AMD + Intel + Apple Silicon + CPU across machines; exo is Apple Silicon (MLX) + CPU-only Linux. 'Your GPUs, not just your Macs' is a defensible wedge exo cannot easily follow.
- Data-local privacy story: 'keep sensitive layers on your own devices' + a full compliance surface (SOC2/HIPAA/GDPR/RBAC docs) matters to regulated verticals — though this is fence, not wedge, and only monetizable once a real customer exists.
- WAN/Internet constellation + OpenAI-compatible serving + multi-language SDKs (Python/TS/Go/Rust) — infra buyers get a self-hosted drop-in OpenAI API with data never leaving their devices.

## Threats

- exo's head start on the exact wedge: ~46.8k stars, polished consumer UX, active 2026 development on the 'pool your devices' category DistLLM wants to own, and wholly absent from DistLLM's own competitive-analysis — a blind-spot threat to star/traction (finding on stale competitive-analysis).
- Ollama/llama.cpp adding cross-MACHINE sharding: the single highest-severity structural threat because it would hand DistLLM's cleanest wedge to a 174k-star community with better onboarding.
- Performance credibility collapse: measured single-node throughput (92 tok/s) is uncompetitive and sub-linear scale-out (1.66x at 2 nodes) means 'pooling = faster' is weakly supported; an HN/benchmark thread that shows empty TTFT/ITL tables or 'illustrative' 70B figures will dismiss the project (findings #226, #232).
- Trust breakers in shipped code: cross-model cache lookup can return WRONG prompt's KV data for a different model (cross_model_prefix_sharing.py:159-175, verified must-fix #46); RED metrics never recorded (verified must-fix #72). Any public repro of cross-model data contamination in the feature being sold is fatal.
- Newer entrants on WebGPU/browser-inference (zero-install GPU pooling) maturing in Safari/Firefox could remove the install barrier — DistLLM's own WebGPU contribution path (webgpu_manager.py) is currently decorative (#111), so it has no ready answer.
- Doubling of the security/correctness surface from 232 audit findings (46 verified must-fix, 5 Critical) across 792 modules creates a perception that breadth outran verification; unusable/dead modules (redundancy>1 always fails, #129) make the 'production-grade' claim fragile against adversarial review.

## Most under-built (by business value)

- Measured performance evidence — TTFT/ITL tables for RTX 4090 and 2-node are EMPTY (docs/BENCHMARKS.md:127-135), 70B '52-68 tok/s' figures are illustrative website numbers not BENCHMARKS.md runs (PERFORMANCE_COMPARISON.md:49-51), single-node throughput (92 tok/s) uncompetitive. The pitch's empirical backbone is missing (findings #226/#232).
- The core pooling CORRECTNESS — cross-model cache can return KV data for a DIFFERENT prompt/model (src/distllm/core/cross_model_prefix_sharing.py:159-175, verified must-fix #46); RED metrics never recorded (verified #72). The very feature being sold has a silent data-contamination landmine.
- First-run onboarding — TASKS-011..015 (one-command install on 3 OSes, HF Spaces live demo, honest benchmark blog, RBAC matrix) all unchecked; install.sh and website/js/calculator.js exist but the live demo, benchmark blog post, and real RBAC CLI don't; no cross-OS installer test (TASKS.md lines 71-100).
- The Ollama multi-device on-ramp — the highest-leverage distribution wedge per finding #230 and the project's own competitive-analysis ('Ollama multi-device gap', 174-175k stars) is entirely unbuilt; no integration in TASKS.md.
- Minimal billing/monetization — MARKETING.md's 7-tier matrix references src/distllm/billing which does NOT exist (verified), so no enterprise license, marketplace take-rate, or metering can be sold today (finding #229).

## Most over-engineered

- Byzantine fault tolerance — src/distllm/dist/byzantine.py is 2,193 lines implementing consensus/BFT for a LAN/WiFi consumer GPU pool where nodes are trusted friends/devices; this is a datacenter-grade correctness apparatus with no plausible near-term user (austerity target).
- DaaS / GPU-hub marketplace — src/distllm/dist/daas_server.py (514 lines) + src/distllm/dist/daas/ (usage_meter, tenant_dispatcher, marketplace_integration, resource_isolation) build a multi-tenant monetization layer with dual-sided payments BEFORE any renter/provider or billing exists; premature liquidity machine (findings on moonshot breadth).
- Edge/WAN federation + disaggregation + privacy stack — edge_federation.py (426), federation.py (1099), disagg/, plus federated learning / differential-privacy RDP accounting (#95, non-subsampled, no integration) compose an enterprise privacy story (federated fine-tuning, DP) for a product that has not yet proven single-cluster multi-device reliability.
- WebGPU browser-GPU contribution — webgpu_manager.py registers browser GPUs but the shipped client never routes compute through them; a genuinely directional zero-install differentiator that today is dead code (#111) — either finish it or demote it.
- Exhaustive scheduler/optimizer/arbitrage surface — core/advanced_scheduling has 13 modules (energy, federated, multi_objective, predictive, preemption, wan, token_bank...) plus arbitrage_engine.py (606) whose CloudArbitrageEngine only generates HOMOGENEOUS plans (#157) — a huge, partly-aspirational optimization plane ahead of measurable demand.
- Backend breadth without verification — ~16 backend adapters (vLLM, llama.cpp, MLX, Ollama, NIM, TGI, Triton, TensorRT, ExLlamaV2, ONNX, PyTorch, WebGPU...) with NO conformance suite asserting each available backend can load+forward (#173), and TASKS-017 itself proposes tiering TensorRT/ExLlamaV2/ONNX to deprecated.

## Monetization angles

- Enterprise self-hosted node license — $1K/node/yr (min 2 nodes) bundling SSO/RBAC, SOC2 Type II, HIPAA BAA, air-gapped deploy, immutable audit logs, 4hr SLA (MARKETING.md:101-123). The most realistic near-term line because regulated verticals (healthcare/finance/legal) are the exact buyers whose data-locality need DistLLM uniquely serves. Strong unit logic: $1K/node/yr is a small fraction of a $1.6-2K RTX 4090.
- GPU reputation marketplace / DistLLM Hub — 10% take-rate, 85% provider payout, escrow, reputation system (MARKETING.md:59-96). Ties directly to the network-effect moat, but needs install base + billing; sequence AFTER distribution (moves 1-3) not before.
- Ollama Cluster Plugin — $5/mo individual / $50/mo team (MARKETING.md:201) — a low-touch willingness-to-pay probe on the biggest local-LLM audience; negligible revenue but tests pricing and feeds the on-ramp (move 3).
- Managed cloud PAYG ($0.15/GPU-hr, Pro $50/mo) — DEFER until billing exists; marketing a free '10 GPU-hr/mo' cloud funnel with no billing engine risks the most-generous-open-core virality claim (finding #229).
- Enterprise privacy add-ons (future) — federated fine-tuning / differential-privacy RDP accounting (#95) at $500/mo (MARKETING.md:135) only once real regulated demand appears; the DP module today is non-subsampled and unintegrated, so this is far-term optionality, not a current line.

## Differentiation levers

- Own a category with a singular message: 'Ollama, but across all your machines and all your GPUs' / 'pool your GPUs' — the one defensible wedge (finding #225/#230); exo can't do NVIDIA/AMD, Ollama can't cluster, vLLM is datacenter-only.
- Heterogeneous multi-vendor pooling (NVIDIA + AMD + Intel + Apple Silicon + CPU) over LAN/WiFi/Internet with auto-discovery, auto-partitioning, node recovery, straggler handling, and WAN token-accumulation — the runtime moat, roughly matched by code.
- Backend-agnostic breadth (~16 adapters incl. vLLM, llama.cpp, MLX, Ollama, NIM, TGI, Triton) — every hardware/quant advance in the ecosystem becomes a DistLLM capability; exo is MLX-only, Ollama is llama.cpp-only.
- Zero-install WebGPU browser-GPU contribution as a future difference — genuinely directional ('contribute your browser GPU to the pool'), but only real once the end-to-end path is built (#111, today decorative).
- Data-local + privacy story positioned for regulated verticals (SOC2/HIPAA/GDPR, keep sensitive layers local) — a fence that only pays once a real compliance customer exists, but the strongest enterprise wedge after raw pooling.
- OpenAI-compatible server + multi-language SDKs (Python/TS/Go/Rust) 'drop-in inference with data on your devices' — but SDK parity must be fixed (#192/#195) before it is a differentiator, not a liability.

## Top 5 sequenced strategic moves

### 1. Move 1 — Close the performance/evidence gap: run and publish honest TTFT + ITL + throughput for 4090 single-node and 2/3/4-node, fill the empty BENCHMARKS.md:127-135 tables, measure real 70B scaling, and publish one 'DistLLM vs baseline' benchmark blog with the accept-anything-honest rule (win on what-you-can't-run + data-local, concede raw speed).
- **Market angle:** This is the credibility backbone for ALL adoption and YC/enterprise diligence. Repivots the story from the vulnerable 'pooling = faster-by-Nx' to the defensible 'runs models you can't otherwise run on hardware you own, data never leaves your devices' (finding #227/#232).
- **Why now:** Empty latency tables and illustrative 70B claims are the most likely 'Show HN -> dismissive benchmark thread' trigger today; the 2026-07-14 laptop preview (TTFT 24.4ms, BENCHMARKS.md:229) shows the data is obtainable cheaply. This is the audit's #1 single adoption risk (#226) and the unbuilt TASK-015.
- **Effort:** Low-Medium (days of bench runs + one blog/README update + TASKS.md status pass) · **Expected outcome:** Raw evidence evaluators trust, an explicit sub-linear scaling-ceiling curve (removes the worst dismissal vector), and conversion of the biggest apparent weakness into an honest strength; unblocks every later move.

### 2. Move 2 — Make the first run win: ship the one-command install on macOS/Linux/Windows/WSL (install.sh exists but TASKS-011 is unchecked and untested on 3 OSes), a live HF Spaces demo of a tiny model, and a flawless 2-machine quickstart, while fixing the critical pooling bugs that poison the featured path (cross-model KV contamination #46, RED metrics #72).
- **Market angle:** Onboarding funnel is the second distribution lever after evidence; the README CLI flow ('distllm cluster start/join') is already the right shape. A dead/live demo and a 2-machine win converts stargazers -> installs.
- **Why now:** TASKS.md Strategic items (011-015) all remain unchecked and hf-spaces/blog do not exist; the cross-model cache bug (#46) is verified-real and sits in the vendored pooling capability, a trust landmine.
- **Effort:** Medium (installer + one HF Space + 2-node quickstart doc + two regression-gated bug fixes) · **Expected outcome:** A repeatable 'works in <10 minutes across 2 machines' demo, demonstrable correctness on the core feature, and the conversion baseline for Ollama-wedge users.

### 3. Move 3 — Build the Ollama multi-device on-ramp: a drop-in 'join this machine to a cluster' path that preserves Ollama model/pull UX and is backed by the existing Ollama/llama.cpp backend + auto-discovery + WideArea; position it as 'Ollama, but across all your machines'.
- **Market angle:** The highest-leverage distribution wedge DistLLM has not built (finding #230): converts ~174k-star Ollama audience into installs without creating a new category from cold, and is the fastest path to network-effect install base.
- **Why now:** Docs/competitive-analysis.md itself names the 'Ollama multi-device gap' and prices an 'Ollama Cluster Plugin $5/mo' (#230), yet no integration is listed in TASKS.md; Ollama must not add multi-machine sharding first (structural threat #2).
- **Effort:** Medium-High (integration with the existing Ollama/llama.cpp backend + a join flow on top of working discovery) · **Expected outcome:** Distribution via the largest existing local-LLM audience, a populated install base that feeds both the perf case and the marketplace moat, and a low-touch $5/mo plugin revenue trial.

### 4. Move 4 — Monetize in the right order: ship minimal billing for the two realistic lines — an enterprise software license ($1K/node/yr with SOC2/HIPAA/SSO) and a marketplace take-rate (10% Hub) — and DEFER the managed cloud PAYG tier (finding #229).
- **Market angle:** MARKETING.md's 7-tier matrix is a sophistication fan-out whose linchpin ('billing', referenced at MARKETING.md:355) is unimplemented (verified: no src/distllm/billing). Gambling founder time on an unbuyable managed cloud first risks the 'most-generous open-core' virality claim; license + marketplace match actual enterprise/data-sovereignty demand.
- **Why now:** Regulated verticals are the one segment whose need (data locality + compliance) matches DistLLM exactly; the audit (#229) says sequence license + marketplace now and hold cloud until a real customer requests it.
- **Effort:** Medium (minimal metering + Stripe + marketplace escrow for a small pilot) — and explicitly REMOVE the billing over-claim from docs until it ships · **Expected outcome:** First real revenue without burning years on managed infra; a priced-without-lying deck that survives diligence; marketplace liquidity once install base exists.

### 5. Move 5 — Harden and tighten scope: make the OpenAPI spec the single source of truth and gate cross-SDK parity in CI (add Rust streaming, JS/Go extended surface — findings #192/#195), delete or EXPERIMENTAL-flag the decorative moonshot modules (Byzantine fault tolerance, DaaS marketplace, federated/DP accounting #95, WebGPU #111, cloud-arbitrage homogeneous-only #157), and run one backend-conformance suite (#173).
- **Market angle:** The 232-finding audit (46 must-fix) shows a wide, under-verified surface; a smaller honest core beats a huge unverifiable one for a tool whose pitch is 'production-grade.' Multi-SDK parity and a backend conformance suite are differentiators once fixed, and de-scoping stars/trust by shrinking attack surface.
- **Why now:** These are cheap, high-leverage hardening steps that can ride alongside moves 1-3; the heterogeneous cloud-arbitrage improvement (#157) is the one that can be productized later as a real $/token feature once backends are trusted.
- **Effort:** Low for spec/CI + flagging (days); Low-Medium for Rust streaming parity; Low for the conformance suite · **Expected outcome:** One contract across 5 SDKs (removes silent per-language drift), no streaming gap for Rust/Go/JS, and a trustworthy 'what ships vs aspirational' surface that sustains the production-grade claim.

## Docs & onboarding assessment

Over-produced and under-verified, and it risks the conversion the audit cares about most. Strengths: the README headline and QuickStart are tight and correctly target the wedge ('Pool GPUs from every device... run models no single machine can handle', 'distllm cluster start/join'), and the docs surface is genuinely deep (ARCHITECTURE, HYBRID_CONTROL_PLANE, MIGRATIONS_*, SDK_REFERENCE, SLA_TIERS, air-gapped, GPU marketplace). But the docs are ahead of shipped reality in the very ways evaluators and investors read FIRST: MARKETING.md (line 355) points at a billing package that does not exist (verified no src/distllm/billing); YC_STARTUP_PACKAGE asserts 'working product, real users' while the one-command installer (TASKS-011), live HF Spaces demo (TASKS-012), TCO calculator live lead-gen, RBAC matrix, and benchmark blog (TASKS-014/015) all remain unchecked; BENCHMARKS.md canonical TTFT/ITL tables are EMPTY (127-135) and the 70B scaling figures are labeled 'illustrative, not a BENCHMARKS.md run' (PERFORMANCE_COMPARISON.md:49-51); TASKS.md shows all 18 tasks unchecked; and the June-2026 competitive-analysis omits the closest real 2026 competitor (exo). The volume of enterprise/compliance/legal docs (TERMS, GDPR, EXPORT_CONTROLS, cybersecurity annexes) is disproportionate for a pre-revenue tool and creates a 'blueprint, not a product' impression. Recommended: insert one 'Status: Shipped vs Planned' matrix near the top of README + docs index (finding #231 reuses the 11-Platform-Services _map), kill or gate the billing/'real users'/live-demo claims until they exist, add the honest scaling curve to benchmarks, and re-order so evidence and onboarding docs land before aspirational enterprise docs.
