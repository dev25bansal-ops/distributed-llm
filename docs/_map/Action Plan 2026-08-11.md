## Executive summary (strategic)

DistLLM's single defensible capability is heterogeneous consumer multi-device pooling (RTX/AMD/Apple Silicon/CPU over LAN/WiFi/Internet to run models no one machine can hold) — audit finding #225 confirms the codebase roughly matches that claim, and the README already anchors on it. But the build is 'wide, not proven': 792 source modules with dozens of decorative moonshot subsystems (Byzantine fault tolerance, DaaS marketplace, federated/DP, WAN disaggregation, WebGPU) exist while the measured evidence the whole pitch depends on is thin. The TWO hard truths: (1) performance credibility is the #1 adoption blocker — single-node throughput (92.0 tok/s on RTX 4090, BENCHMARKS.md:197) is uncompetitive, the canonical TTFT/ITL tables for 4090 and 2-node are still EMPTY (BENCHMARKS.md:127-135), the 70B '52-68 tok/s' scaling figures are 'illustrative' website numbers, not BENCHMARKS.md runs, and the only real scale-out number is sub-linear (2 nodes = 153.1 tok/s = 1.66x, 83.2% efficiency, BENCHMARKS.md:198); (2) docs over-claim vs reality — MARKETING.md references a src/distllm/billing package that does not exist (verified: NO billing dir), YC_STARTUP_PACKAGE asserts 'working product, real users,' and the June-2026 competitive-analysis omits the closest real 2026 competitor, exo (~46.8k stars, Apache-2.0, the same 'pool your devices' pitch on Apple Silicon). Strategic priorities: close the perf/evidence gap, make first-run win on 3 OSes, build the Ollama multi-device on-ramp as the distribution wedge, monetize the enterprise license + marketplace before the (unbuilt) managed cloud, add OpenAPI-gated SDK parity, and cut/defer the unverifiable surface.

## P0 issues — block any release (fix first)

- **[High] 🔒 · CVSS 9.1** JWT authentication bypass via algorithm confusion in HS256 fallback validator — `src/distllm/plugins/auth_plugin.py:168` — Full authentication bypass and privilege escalation to admin for any deployment running without PyJWT when an asymmetric signing key or a short shared secret is configured: an attacker forges a token valid against the shared secret (or uses the token's own public-key material) and is treated as authenticated. Root-trust compromise of the API layer.
- **[Critical] 🔒** Cross-model sibling cache lookup returns KV data for a DIFFERENT prompt (wrong/injected tokens) — `src/distllm/core/cross_model_prefix_sharing.py:169` — Wrong/cross-tenant generations in shared-base serving: a cached KV prefix for prompt A is replayed as the prefix for prompt B, injecting foreign tokens into completions and exposing stored content across prompts/tenants. - **[High] 🔒 · CVSS 7.5** Exact-match cache key is not tenant/user scoped - cross-tenant response leak — `src/distllm/plugins/cache_plugin.py:83` — Cross-tenant disclosure of private cached LLM responses in any multi-tenant deployment with caching enabled. - **[High] 🔒 · CVSS 8.6** Unauthenticated HA heartbeat/snapshot fail-open when DISTLLM_HA_SECRET is unset -> leader-election takeover and coordinator state injection — `src/distllm/api/server.py:1434` — Unprivileged takeover of HA leader election and injection of a full coordinator state snapshot (fake nodes/metadata) across the cluster from an unauthenticated socket.

- **[High] 🔒 · CVSS 8.8** Federated LoRA merge accepts untrusted adapters + self-reported dataset_size -> model poisoning and unfair weight dominance — `src/distllm/dist/federated_merge.py:193` — One compromised node poisons the global adapter or dominates the weight average, corrupting the artifact every node later adopts in federated multi-node training.

Privacy/trust claim is false advertising with real enforcement harm.
- **[High] 🔒** Aether 'secure' aggregation is a no-op and its pairwise masks use a single public seed — `src/distllm/core/federated_finetuner.py:178` — Non-deterministic, unstable federated training under any straggler/failure; round-mixing corrupts averages; the advertised secure-masking protection is breakable. Linked to the fake 'secure aggregation' claim that is a headline differentiator.

**Spot-check — top P0 issues vs the code:**

- **CONFIRMED** — JWT authentication bypass via algorithm confusion in HS256 fallback validator (src/distllm/plugins/auth_plugin.py:168)
  - *Bug is real. _validate_jwt_hs256 (auth_plugin.py:155-191) verifies only an HMAC-SHA256 of header.payload with the configured secret; it never inspects the token's alg header, never enforces key-type, and aud/iss are checked only if present in the payload (validate_jwt fallback lines 240-253). PyJWT is NOT declared in pyproject.toml or requirements.lock, so the fallback is a reachable default path whenever DISTLLM_AUTH_SECRET is set. Nuance on the claim 'accepts any 3-part token signed with a PUBLIC asymmetric key': the HMAC gate is real, so forgery requires knowing/guessing the secret material. The genuine bypass conditions are (a) a short/guessable DISTLLM_AUTH_SECRET (only a warning for <32 chars, lines 302-306) or (b) algorithm confusion when the secret is a PEM public key (the PyJWT path auto-detects RS256, but the fallback HMACs with the public PEM text, which is public, so anyone can forge HS256 admin tokens). Priority P0, effort 2-4h, Day 1 are sane; CVSS 9.1 is defensible under those conditions.*
- **CONFIRMED** — Cross-model sibling cache lookup returns KV data for a DIFFERENT prompt (src/distllm/core/cross_model_prefix_sharing.py:169)
  - *Method-level bug confirmed: the sibling branch (lines 168-181) iterates every cached entry and returns the first entry whose source_model shares the query model's base_model with shared_layers>0, never comparing token_ids or prefix_hash — direct/base branches key on prefix_hash but the sibling branch does not. Correction to the impact: the current known consumer ClusterPredictivePrefetcher (cluster_predictive_prefetcher.py:115-117 stores kv_data=None; lines 165-173 use lookup only as a WarmStartSource.CROSS_MODEL hit signal) does not replay entry.kv_data, so today's reachable harm is a wrong cross-model hit (inflated hit stats / premature warm-start), not injected foreign tokens in completions. The token-injection/data-exposure impact is the class's documented contract for any consumer that replays entry.kv_data, so the bug is dangerous but 'Critical' severity is arguably one notch high given current wiring. P0 + effort 2-4h + Day 1-2 fix are still sane.*
- **CONFIRMED** — Unauthenticated HA heartbeat/snapshot fail-open when DISTLLM_HA_SECRET is unset (src/distllm/api/server.py:1434)
  - *Fully confirmed. AuthMiddleware exempts /api/v1/ha/heartbeat (middleware.py:225-232), and the route gates X-HA-Secret only inside `if expected_secret:` where expected_secret=os.environ.get('DISTLLM_HA_SECRET','') — an empty default is falsy, so with the env unset an unauthenticated request proceeds to parse the body. Impact confirmed end-to-end: handle_heartbeat_request (ha_coordinator.py:216-268) adopts a higher term (forces step-down, lines 244-250) and, once the node is FOLLOWER, applies attacker-supplied peer_state via _on_leader_state (coordinator_election.py:171-180) -> apply_state_snapshot (lines 131-157) -> manual_register of arbitrary fake nodes after _sync_standby_status flips _is_standby True (lines 159-169). So both leader-election takeover and node-table/state injection are real. P0, CVSS 8.6, effort 3-5h, Day 1-2 all sane. Minor scope note: impact requires HA mode enabled (coordinator has an _ha_election); not reachable on non-HA coordinators.*
- **CONFIRMED** — Kademlia DHT STORE is unauthenticated and token-unverified (src/distllm/dist/p2p/kademlia_dht.py:834)
  - *Confirmed exactly as described. The client attaches a token at store() (line 651, 'token': self.local_node.hex_id) but _handle_store (lines 834-858) never reads params.get('token') and never validates it; _dispatch_request (lines 384-414) does no source/signature check before routing to the handler. Any node able to reach the UDP DHT port can write arbitrary key->value bytes into self._store with EXPIRE_TIME, and FIND_VALUE/FIND_NODE then serve those poisoned values. P0, CVSS 8.8, effort 3-5h, Day 2-3 sane. Only scope note: impact is gated on the DHT listener binding to a reachable interface (WAN-reachable if so configured, which is the DHT's purpose).*
- **CONFIRMED** — RED metrics (requests/latency/duration/errors) are never recorded - .labels() handles are discarded (src/distllm/api/observability_middleware.py:124)
  - *Core claim confirmed and actually worse. _record_metrics (lines 117-136) builds labeled handles for requests_total/request_latency/request_duration_seconds/errors_total and discards them with no terminating .inc()/.observe(), while the cost metrics on the same lines correctly call .inc(cost_val)/.inc(gpu_val) (lines 143-149). A grep across src/distllm finds zero .inc()/.observe() calls on any of the four RED metrics anywhere. Correction to the description: the finding states ObservabilityMiddleware 'is the sole wiring for the Prometheus exporter's request metrics', but the middleware is never mounted at all — server.py neither imports it nor calls app.add_middleware(ObservabilityMiddleware) (the only hits repo-wide are the class definition, its docstring, and an audit report). So the .labels() code is unreachable dead code and the metrics are doubly unrecorded. The fix therefore also requires wiring the middleware (or an equivalent) into the app, not just appending .inc()/.observe(). P0, effort 1-2h, Day 1 remain sane.*
- **CONFIRMED** — Pipeline cross-node gRPC is plaintext by default (src/distllm/dist/node_client.py:365)
  - *Confirmed. create_node_client defaults use_tls=False (line 173) and falls through to grpc.insecure_channel(target) (line 225); forward_request (line 365) and forward_request_async (line 433) both call create_*_node_client without passing use_tls, so the main pipeline-parallel path sends hidden states and KV caches unencrypted (cluster_key is an auth token, not encryption). Server side matches: NodeServer TLS is gated on settings.tls.enabled and coord_tls defaults False (server.py:1799-1807). P0, CVSS 7.4, effort 4-8h, Day 3-5 sane. One fairness note: plaintext-by-default may be a deliberate LAN trust-model choice, but it contradicts the project's documented TLS posture and is an exposure over Internet/federation paths.*
