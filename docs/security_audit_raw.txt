## CRITICAL SEVERITY

### 1. `zero_copy.py:66` — Unrestricted pickle.loads on external input

- **File:** `D:/distributed-llm/src/distllm/dist/zero_copy.py`
- **Lines:** 55-56, 65-66
- **Severity:** CRITICAL
- **Category:** Insecure Deserialization (CWE-502)
- **CVSS:** 9.8 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H)
- **Description:** `import_tensor` calls `pickle.loads(ipc_handle)` on line 66 on bytes passed in as a parameter. The current caller in `recv()` (line 214) hardcodes `b""` as the handle, which safely raises and is caught. But the method signature accepts arbitrary attacker-controlled bytes. If any future code path passes attacker-controlled data to `import_tensor`, this is instant remote code execution. The corresponding `export_tensor` (lines 55-56) also uses pickle.dumps, making the round-trip an end-to-end pickle chain.
- **Remediation:** Replace pickle with a safe serialization format (JSON + base64, msgpack, or protobuf). Never use pickle for cross-trust-boundary data. Add type checking and input validation. Implement a safelist of allowed reduction functions.

### 2. `block_transfer_service.py:208` — Insecure gRPC channel with no authentication

- **File:** `D:/distributed-llm/src/distllm/dist/block_transfer_service.py`
- **Lines:** 208
- **Severity:** CRITICAL
- **Category:** Missing Authentication (CWE-306), Cleartext Transmission (CWE-319)
- **CVSS:** 9.1 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N)
- **Description:** `fetch_blocks` creates `grpc.insecure_channel(self._address)` — an unencrypted, unauthenticated gRPC channel. Additionally, the `BlockTransferStub` class referenced on line 211 is never defined anywhere in the file — the try/except `ImportError` on grpc masks this as a no-op.

### 3. `cross_cluster.py:82` — No authentication on cross-cluster forwarding

- **File:** `D:/distributed-llm/src/distllm/dist/cross_cluster.py`
- **Lines:** 82 (and all call sites: 91, 194, 226)
- **Severity:** CRITICAL
- **Category:** Missing Authentication (CWE-306)
- **CVSS:** 9.8 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H)
- **Description:** `forward_request` sends HTTP POST requests to arbitrary URLs with only a spoofable `X-Forwarded-From: federated` header. ## HIGH SEVERITY

### 4. `cross_cluster.py:82,91,194,226` — SSRF via allow_private_hosts=True

- **File:** `D:/distributed-llm/src/distllm/dist/cross_cluster.py`
- **Lines:** 82, 91, 194, 226
- **Severity:** HIGH
- **Category:** Server-Side Request Forgery (CWE-918)
- **CVSS:** 8.8 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N)
- **Description:** All four call sites pass `allow_private_hosts=True` to `safe_urlopen`, which disables the DNS-rebinding-protected private-IP check in `security/utils.py`. An attacker who controls the `remote_coord_url` or poisons the peer list can make the server perform arbitrary HTTP requests to internal network services (Redis, Elasticsearch, cloud metadata endpoints like `169.254.169.254`, etc.).
- **Remediation:** Remove `allow_private_hosts=True` from all cross-cluster calls. If private-host access is genuinely needed for cross-datacenter federation, maintain an explicit allowlist of peer IPs/ranges rather than blanket-permitting all private addresses. Validate all peer URLs against the allowlist at the caller site, not deep in the transport helper.

### 5. `node_service.py:468` — No client certificate verification in TLS mode

### 6. `node_service.py:470` / `node_client.py:113` — Insecure plaintext gRPC fallback

- **File:** `D:/distributed-llm/src/distllm/dist/node_service.py` line 470 and `D:/distributed-llm/src/distllm/dist/node_client.py` line 113

### 7. `gossip.py:97-122` — Unauthenticated gossip when no global HMAC key is set

- **File:** `D:/distributed-llm/src/distllm/dist/p2p/gossip.py`
- **Lines:** 97-122
- **Severity:** HIGH
- **Category:** Missing Authentication for Critical Function (CWE-306)
- **CVSS:** 7.5 (AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:H/A:N)
- **Description:** When `DISTLLM_GOSSIP_HMAC_KEY` is not set, each node generates its own node-local key (line 113). This key is never shared with peers. Consequently, gossip advertisements between different nodes carry a signature that no other node can verify. ### 8. `gossip.py:514` — Page advertisements bypass HMAC verification

### 9. `node_client.py:108-110` — No hostname verification in gRPC TLS credentials

### 12. `federation.py:183-185` — No custom TLS verification for federation HTTP clients

### 21. `privacy.py:175-178` — Approximate inverse leaks information through reconstruction error

- **File:** `D:/distributed-llm/src/distllm/dist/privacy.py`
- **Lines:** 134-137, 158-161, 175-178
- **Severity:** LOW
- **Category:** Privacy Violation (CWE-359)
- **CVSS:** 3.7 (AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:N/A:N)
- **Description:** For hidden_size > 2048, `restore()` uses `projection.t() / hidden_size` (transpose + scalar divide) as an approximate inverse of the random projection. This is not a true inverse of a random orthogonal matrix, resulting in signal degradation and potential information leakage patterns that a determined adversary could exploit to recover approximate activations.
- **Remediation:** Use `torch.linalg.pinv` (pseudo-inverse) instead of transpose division for matrices > 2048, or generate the projection as an orthogonal matrix (QR decomposition of random matrix) for which transpose is the true inverse.
